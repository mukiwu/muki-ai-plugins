# 程式碼審查（Review Code）

## 定位

審查一段改動，回答三個問題：

- **規範**：寫法符不符合這個 repo 的規範
- **需求**：有沒有照 issue 或 spec 要求的做
- **Bug**：會不會在執行時出錯

三個角度分開審，是因為一段程式碼可能只過其中一關：照規範寫但做錯功能、功能對了但壞了慣例、兩者都對卻在邊界條件出錯。分開報告，一個角度的問題才不會被另一個角度蓋過去

找問題的子代理容易誤報，而且同一個子代理很難推翻自己的判斷。所以重要的發現會再交給沒看過前面推理的子代理獨立判斷，多數同意才列進報告。報告越乾淨，作者越能放心照著修

## 硬規則

1. **唯讀**：不修改任何程式碼、測試或設定，修正交給呼叫的人
2. **每條發現都要有位置與證據**：寫明檔案與行號，引用相關的程式碼；沒有證據的推測不列
3. **不重複既有工具的工作**：lint、型別檢查、formatter 會擋下的問題不列
4. **審測試本身不在這裡**：測試有沒有假綠燈、有沒有貼實作細節，交給 `review-tests`

## 輸入

- **基準點**：commit SHA、分支、tag、`main`、`HEAD~3` 都可以；使用者沒給就先問，不要自己猜
- **需求來源**：可以直接給路徑；沒給就照第 2 步去找
- `--quick`：跳過投票，只跑三個角度的審查，適合小改動或還在來回修的時候

## 流程

### 1. 確認 diff

- 先用 `git rev-parse <基準點>` 確認基準點存在
- 用 `git diff <基準點>...HEAD`（三個點，對照分岔點）取得 diff，用 `git log <基準點>..HEAD --oneline` 列出 commit
- diff 是空的就在這裡停下來告訴使用者，不要派子代理去審空的東西

### 2. 找需求來源

依序找：

1. commit 訊息裡的 issue 編號（`#123`、`Closes #45`），用 `gh issue view` 讀內容
2. 使用者給的路徑
3. `docs/`、`specs/`、`.scratch/` 底下檔名和分支或功能相符的 spec
4. 都找不到就問使用者；使用者說沒有，需求角度就略過，並在報告裡註明

### 3. 找規範來源

- repo 裡寫明寫法規範的檔案，例如 `CODING_STANDARDS.md`、`CONTRIBUTING.md`，以及它們引用的共用規範
- repo 有 `docs/lore/` 時，把和改動檔案相關的 `pitfalls.md`、`business-rules.md` 一起交給規範角度
- 不論 repo 有沒有寫規範，都附上下面這份程式碼異味清單（出自 Fowler《重構》第三章）。兩條原則：
  - repo 的規範優先，repo 明確允許的寫法就不要再用異味清單挑
  - 異味一律是判斷題，寫成可能有某某異味，不當成硬性違規

| 異味 | 怎麼認 | 怎麼修 |
|---|---|---|
| Mysterious Name | 名稱看不出它在做什麼或裝什麼 | 改名；想不出誠實的名字，代表設計本身不清楚 |
| Duplicated Code | 同樣的邏輯出現在這次改動的兩個以上地方 | 抽出共用的部分，兩邊都呼叫它 |
| Feature Envy | 一個函式用別的物件的資料比用自己的還多 | 把函式搬到它依賴的資料旁邊 |
| Data Clumps | 同幾個欄位或參數總是一起出現 | 包成一個型別再傳 |
| Primitive Obsession | 用字串或數字代表一個該有自己型別的領域概念 | 給這個概念一個小型別 |
| Repeated Switches | 同一個型別的 switch 或 if 串在多處重複 | 改用多型，或讓各處共用同一張對照表 |
| Shotgun Surgery | 一個邏輯上的改動，要改散落在很多檔案的地方 | 把會一起變動的東西收進同一個模組 |
| Divergent Change | 同一個檔案為了好幾個不相關的理由被修改 | 拆開，讓每個模組只為一個理由改 |
| Speculative Generality | 為需求裡沒有的情況預先加的抽象、參數或掛勾 | 刪掉，等真的需要再加 |
| Message Chains | 呼叫端依賴一長串 `a.b().c().d()` 的走訪 | 在第一個物件上提供一個方法把走訪藏起來 |
| Middle Man | 一個類別或函式幾乎只是把呼叫轉給別人 | 拿掉中間層，直接呼叫真正的目標 |
| Refused Bequest | 子類別或實作者忽略或覆寫了大部分繼承來的東西 | 不用繼承，改用組合 |

### 4. 三個角度平行審查

在同一則訊息裡派三個 `general-purpose` 子代理，彼此看不到對方的 context。每個子代理的 prompt 都要包含 diff 指令、commit 清單，以及下面的共同要求：

- 每條發現寫明檔案與行號、引用相關程式碼、說明為什麼是問題、修正方向
- 每條標上類別：
  - `Important`：會造成錯誤行為、違反硬性規範，或需求沒做到
  - `Nit`：小問題，不修也不會出錯
  - `Pre-existing`：這次改動之前就存在的問題，不算這次要修的範圍
- 同一類問題在同一條裡一次列完所有位置，不要拆成很多條
- 400 字以內

各角度另外附上：

**規範子代理**：第 3 步找到的規範檔路徑、相關的 lore 條目，以及完整的異味清單（子代理讀不到這份 SKILL.md，要整份貼進去）。要求區分硬性違規與判斷題

**需求子代理**：需求來源的路徑或內容。要求列出：需求有但沒做或只做一半的、diff 做了但需求沒要求的、看起來有做但做錯的，每條引用需求原文。沒有需求來源就不派

**Bug 子代理**：要求從執行時會出錯的角度看，包含邏輯錯誤、邊界條件、空值、非同步與競態、錯誤處理、資料遷移與相容性。特別要查：這次改了一個行為，repo 裡還有沒有其他地方做同一件事卻沒跟著改。可以讀整個 repo，不限於 diff

### 5. 投票確認

用 `--quick` 時跳過這一步，並在報告開頭註明沒有經過投票

- 對每條 `Important` 發現，派 2 個新的 `general-purpose` 子代理獨立判斷，可以平行派出
- 給投票子代理的只有：這條發現的描述、檔案與行號、diff 指令；不給原本子代理的推理過程，也不告訴它別人怎麼投
- 要求它自己讀程式碼後回答：成立、不成立或無法判斷，附上一句依據
- 兩票都成立就保留；兩票都不成立就丟掉；意見分歧時再派第 3 個子代理決定
- 投票子代理指出原本的描述有誤但問題仍成立時，用修正後的描述
- `Nit` 和 `Pre-existing` 不投票，`Nit` 最多列 5 條

### 6. 報告

- 用 `## 規範`、`## 需求`、`## Bug` 三個標題分開列，不要跨角度重新排名；三個角度各自先列 `Important`，再列 `Nit`
- 每條 `Important` 附上投票結果，例如 2/2 成立、2/3 成立
- 被投票刷掉的發現收在報告最後一行，只寫數量，例如 投票排除 3 條
- `Pre-existing` 另外放一段，建議開 issue 追蹤，不要混進這次要修的清單；使用者採用 sentry-autofix 的標籤時，可以標 `source:review`，判斷 AI 能修的再加 `fix:ai`
- 最後一行總結：各角度 `Important` 的數量，以及各角度最嚴重的一條

### 7. 多輪審查

作者修完再審時：

- 第二輪起只看上一輪之後新增的 diff，不重審整份
- 上一輪提過、作者已經說明不修的問題，不再重複提
- 審到第三輪還有新的 `Important`，停下來建議作者回頭檢查整體做法，不要繼續逐條修

## 和其他 skill 的分工

- `review-tests`：審測試本身有沒有盲點，和這個 skill 互補不重複
- `lore-guard`：只對照 `docs/lore/` 已記錄的規則；這個 skill 的規範角度會讀相關的 lore，但不取代 `lore-guard` 的完整比對
- 這個 skill 的流程與異味清單參考 Matt Pocock 的 [code-review](https://github.com/mattpocock/skills)，另外加上 bug 角度、發現分類與投票確認
